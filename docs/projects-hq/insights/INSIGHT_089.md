# PROJECTS HQ INSIGHT #089

## Date
6. 10. 2026

## Title
# Provenance Must Travel With the Artifact

---

## Core Idea

Autonomous systems continuously create artifacts:

    research reports
    datasets
    summaries
    code
    signals
    trade proposals
    risk decisions
    configuration changes.

Once an artifact leaves the process that created it,
its surrounding context can disappear.

The next agent may see:

    the artifact

without knowing:

    who created it
    from which evidence
    under which instructions
    using which model
    under which authority
    at what time
    with which validation.

Therefore:

# PROVENANCE MUST TRAVEL WITH THE ARTIFACT.

---

## The Detached Artifact Problem

Imagine:

    Research Agent
        ↓
    "BTC REGIME = BULLISH"
        ↓
    saved to file.

Hours later:

    Trading Agent

reads only:

    BTC REGIME = BULLISH.

What disappeared?

    source data
    timestamp
    confidence
    model version
    methodology
    contradictory evidence
    expiry
    author
    validation status.

The conclusion survived.

Its epistemic context did not.

This is dangerous.

---

## Content Alone Is Insufficient

Two files may contain exactly:

    BUY BTC.

But they may have radically different origins.

Artifact A:

    generated by Research Agent
    from validated market data
    under current strategy policy.

Artifact B:

    copied from social media
    through an untrusted webpage.

Textually:

    identical.

Operationally:

    completely different.

Therefore:

# CONTENT ≠ PROVENANCE.

---

## Provenance Envelope

Every consequential artifact should carry a structured:

# PROVENANCE ENVELOPE.

Example:

    ARTIFACT_ID
    ARTIFACT_TYPE
    CREATED_BY
    CREATED_AT
    MODEL
    MODEL_VERSION
    INPUT_SOURCES
    SOURCE_TIMESTAMPS
    POLICY_VERSION
    AUTHORITY_SCOPE
    VALIDATION_STATUS
    CONFIDENCE
    EXPIRY
    PARENT_ARTIFACTS
    HASH.

Now the artifact carries:

    not only WHAT

but also:

    WHERE FROM.

---

## Lineage

Artifacts should form a traceable lineage.

Example:

    MARKET DATA
        ↓
    FEATURE SET
        ↓
    REGIME CLASSIFICATION
        ↓
    STRATEGY SIGNAL
        ↓
    TRADE PROPOSAL
        ↓
    RISK DECISION
        ↓
    FINAL ACTION ENVELOPE
        ↓
    ORDER.

Each object should reference:

    its parents.

Then a final order can be traced backward.

---

## Trading Example

Suppose Trading Agent receives:

    SIGNAL:
        LONG BTC.

Before using it, the system should be able to ask:

    Who generated this?

    From which market snapshot?

    Which strategy version?

    Which parameters?

    Was it OOS-approved?

    Is it still current?

    Has it been modified?

    Was its parent data trusted?

If these cannot be answered:

    SIGNAL STATUS = UNTRUSTED.

---

## Unknown Origin

A powerful default:

# UNKNOWN PROVENANCE ≠ TRUSTED INPUT.

An artifact without verifiable origin
may still be useful for:

    research.

But it should not automatically enter:

    decision authority.

---

## Provenance vs Authority

Important distinction:

    provenance

does not create:

    authority.

Knowing exactly who produced something
does not mean that producer had permission
to authorize an action.

Therefore:

    PROVENANCE
        tells us
    WHERE IT CAME FROM.

    AUTHORITY
        tells us
    WHAT IT MAY CAUSE.

These must remain separate.

---

## Provenance vs Truth

Another distinction:

    known provenance

does not guarantee:

    correctness.

A perfectly traceable model can still be wrong.

Therefore:

    PROVENANCE ≠ TRUTH.

But provenance allows us to evaluate:

    reliability
    methodology
    freshness
    conflicts
    accountability.

Without provenance,
those evaluations become much harder.

---

## Immutable Identity

Every important artifact should receive:

    ARTIFACT_ID

and ideally:

    CONTENT HASH.

If content changes:

    new hash.

If materially revised:

    new version.

This prevents silent mutation.

---

## Versioned Artifacts

Avoid:

    strategy.md

silently changing forever.

Prefer:

    strategy_id
    version
    timestamp
    parent_version.

Then:

    TRADE_1042

can state:

    generated_under:
        strategy_v1.9r19b.

Future reconstruction becomes possible.

---

## Freshness

Provenance should include time.

Why?

Because:

    correct yesterday

may become:

    dangerous today.

Market artifacts especially require:

    CREATED_AT
    DATA_AS_OF
    EXPIRES_AT.

This connects directly to #084:

    AUTHORITY HAS A HALF-LIFE.

Information can have a half-life too.

---

## Derived Evidence

If Agent B summarizes Agent A:

    Agent B's output

should not erase:

    Agent A's sources.

Instead:

    B
      ↓
    references A
      ↓
    references original evidence.

This creates:

# EVIDENCE LINEAGE.

---

## Multi-Agent Systems

In multi-agent systems,
provenance becomes increasingly important.

Without it:

    Agent C

may treat output from:

    Agent B

as primary evidence,
even though B merely summarized:

    Agent A

which copied:

    untrusted source X.

Repeated transformation can create:

    false legitimacy.

Provenance prevents this.

---

## Sponsored Information

Commercial content introduces another class.

An artifact may carry:

    SOURCE_TYPE:
        advertisement

or:

    SOURCE_TYPE:
        sponsored.

This allows downstream agents
to apply different evidence weighting.

A sponsored claim should not silently become:

    independent research evidence.

---

## Human Inputs

Human instructions also need provenance.

Example:

    USER_APPROVAL
        actor = David
        timestamp = T
        scope = TRADE_1042
        expires = T + 60s.

Now the system can distinguish:

    actual human authorization

from:

    text claiming
    "David approved this."

---

Code artifact:

    commit

    timestamp
    diff

Git already demonstrates
a powerful provenance principle:

    history travels with change.

Projects HQ should extend
the same idea to:

    test result
    reviewer
    resulting commit.

Then code is not merely:

    code.

It is:

    reconstructable code.

    id
    type
    creator
    created_at
    source
    parent_ids
    policy_version
    model_version
    validation_state
    expiry
    content_hash.

Start simple.

## Failure Rule

If required provenance is:

    missing
    invalid
    inconsistent
    expired
    unverifiable

then:

    DO NOT SILENTLY PROMOTE
    THE ARTIFACT TO TRUSTED STATUS.

Instead:

    quarantine
    revalidate
    downgrade confidence
    request human review
    or reject.

---

## Projects HQ Principle

> A consequential artifact should never become detached from the evidence of how it was created. Preserve its creator, sources, parent artifacts, timestamps, policy context, validation state and integrity so downstream agents can distinguish trusted lineage from anonymous content.

Shortest version:

# PROVENANCE MUST TRAVEL WITH THE ARTIFACT.

Operational version:

# CREATE → IDENTIFY → TRACE → VERIFY → USE.
